# Purchase Memory is a separate catalog, not hidden Items

Add-item suggestions used to come from the target List's done Items, so the Done section (_Kúpené_) was both "what I just bought" and the app's only memory: clearing it, deleting a done Item or deleting the List erased the suggestions, and re-adding a suggestion only flipped the same Item back to active, so there was nowhere to count how often something is bought. Suggestions now come from the **Purchase Memory** (`families/{FAMILY_ID}/purchaseMemory/{entryId}`), a family-wide catalog with one document per normalized Item name (`purchaseKey` in `itemService.ts`: trimmed, whitespace collapsed, Slovak-locale lowercase, diacritics stripped; quantities and variants stay in the key). The document id is derived deterministically from that key (`purchaseMemoryEntryId`), so two Members checking off the same name write to the same document without a transaction. Checking an Item off writes the Item patch and the entry (`increment(1)` on the total and on the per-List count, `serverTimestamp()` as the last purchase, the current text) in one `writeBatch`, which is atomic and works offline; nothing ever decrements it — unchecking, deleting, clearing the Done section, deleting a List and moving an Item leave it alone. The Done section becomes a view only, and its button is renamed to "Vyčistiť kúpené".

We considered **hiding done Items instead of deleting them** (a `hidden` flag set by "clear") and rejected it: it brings back the hidden-state concept ADR 0001 deliberately refused for Lists, and every List open would have to read the List's whole purchase history just to build suggestions. We also considered **one aggregated document** holding every name and count, and rejected it: every check-off would ship the whole document to every device, and it has a hard 1 MiB ceiling. An **event log with TTL expiry** (one document per purchase) is the natural basis for a learned store order later; it is postponed, not rejected, and nothing here blocks adding it next to the catalog.

Accepted consequences: an accidental check-off counts (there is no undo yet), per-List counts of a deleted List stay in the entries (harmless, never cleaned up), and a typo stays in the Purchase Memory until it is removed by hand in the Firestore console until a "forget" feature exists. Entries were back-filled once from existing done Items by `scripts/migrate-purchase-memory.ts`, so counts before the switch are an estimate.
