# Fractional indexing for `activeOrder`, not dense integers

`activeOrder` is a float, not a sequential integer. Reordering an Item only writes that one Item's `activeOrder` (e.g., the midpoint between its new neighbors) — it never rewrites the whole active list. We considered dense integer indexing with full renormalization on every reorder, but rejected it: renormalizing requires a batch write across every active Item in the List on every drag, and two Members dragging concurrently on separate devices could race and have one batch clobber the other's reorder entirely. Fractional indexing confines each reorder to a single-document write, so concurrent drags from different Members only affect the moved Item, not the whole list's ordering. This is the standard approach used by tools like Trello and Linear for drag-and-drop with realtime sync. Float precision drift after many reorders is a known, low-stakes tradeoff — acceptable for a family-sized list, and fixable later by an occasional renormalization pass if it ever matters.
