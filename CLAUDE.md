# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mobile-first family shopping list app. Google sign-in, join via invite code, realtime sync of shared shopping lists across family members. Vite + React 19 + TypeScript + Chakra UI, backend is Firebase (Auth, Firestore, Hosting). Domain glossary is in `CONTEXT.md`; architectural decisions with their rejected alternatives are in `docs/adr/`.

## Commands

```bash
npm run dev              # Vite dev server on :5173
npm run check            # single quality gate: lint + lint:cycles + format:check + unit tests + build (build runs tsc -b, so it also typechecks; what CI job 1 runs)
npm run lint:cycles      # madge --circular over src (resolves the @/ alias via tsconfig.app.json)
npm run build             # tsc -b typecheck + Vite production build to dist/
npm run typecheck      # tsc -b over app, node/configs/scripts, e2e and the emulator suites (all strict)
npm run lint               # eslint . --max-warnings 0 (includes curly: all)
npm run format            # Prettier --write (format:check to verify)
npm run test               # Vitest unit project (jsdom, no emulator needed)
npm run test:watch    # Vitest watch mode (unit project)
npm run test:rules       # Firestore security rules tests — wraps itself in firebase emulators:exec, needs JDK 21+
npm run test:integration # Firestore integration tests — wraps itself in firebase emulators:exec, needs JDK 21+
npm run test:emulators   # rules, then integration, inside ONE emulators:exec (what CI runs); they share a projectId so never run them in parallel
npm run test:e2e        # Playwright — does NOT auto-start emulators; spawns its own dev server via webServer
npm run seed               # Generates the (one-time, static) family invite code — requires Firestore emulator already running
npm run migrate:purchase-memory # One-time back-fill of the Purchase Memory from done Items (emulator by default; `-- --production` with GCLOUD_PROJECT)
```

Run a single unit test file: `npx vitest run src/features/items/__tests__/itemService.test.ts`. Run a single rules/integration test file with `--project`, which still needs to run inside `firebase emulators:exec`: `firebase emulators:exec --only firestore,auth "npx vitest run --project integration src/test/items.integration.test.ts"`.

For e2e tests that need a signed-in member (`e2e/mobile-smoke.spec.ts`, `e2e/offline-sync.spec.ts`), the Auth + Firestore emulators must be running separately since Playwright only starts the dev server, not the emulators:

```bash
firebase emulators:exec --only firestore,auth "npm run test:e2e"
```

`e2e/smoke.spec.ts` is unauthenticated and works without emulators.

`vite.config.ts` declares three Vitest projects (`unit`, `rules`, `integration`) that share its `@/` alias and plugins; the npm scripts select one with `--project` (a bare `npx vitest` would run all three, and the emulator ones would fail without an emulator). They are selected by filename suffix: `**/*.rules.test.ts` and `**/*.integration.test.ts` belong to their emulator projects (the unit project excludes both globs); every other `*.test.ts(x)` is a unit test. A new suite just needs the right suffix. The emulator suites are typechecked via `tsconfig.emulator-tests.json`; the four tsconfigs all extend `tsconfig.base.json`.

Tooling: Prettier (no semicolons, single quotes, 80 cols; markdown not formatted) and ESLint are enforced by a husky pre-commit hook (lint-staged: `eslint --fix` + `prettier --write`, no tests) and by CI (`.github/workflows/ci.yml`: `npm run check`, plus `test:emulators` with Java 21; e2e is not in CI). Node version is pinned in `.nvmrc` (24).

## Firestore data model

Single-tenant: one Firebase project = one Family, forever. `FAMILY_ID` (`src/constants/family.ts`) is a hardcoded constant, never looked up at runtime — there is no multi-family concept anywhere in the code.

```
families/{FAMILY_ID}                          (fixed id)
families/{FAMILY_ID}/members/{uid}            membership doc; existence = "is a member"
families/{FAMILY_ID}/lists/{listId}           name, createdAt, createdBy
families/{FAMILY_ID}/lists/{listId}/items/{itemId}
families/{FAMILY_ID}/purchaseMemory/{entryId} Purchase Memory: text, purchaseCount, lastPurchasedAt, countByList
invites/{inviteCode}                          one-time, generated by scripts/seed.ts, never via UI
```

The **Purchase Memory** (ADR 0004) is where add-item suggestions come from, not the Done section (_Kúpené_): one entry per `purchaseKey(text)` (trimmed, whitespace collapsed, Slovak lowercase, no diacritics), id `purchaseMemoryEntryId(key)` (deterministic, escapes what Firestore ids forbid). `checkItem` takes the Item's text and writes the Item patch plus `increment(1)` on the entry's total and per-List count in one `writeBatch` (atomic, offline-safe, no transaction needed); nothing else touches the entries and nothing decrements them. `usePurchaseSuggestions` (one `subscribePurchaseMemory` per screen) hands `AddItemForm` a `suggest(text)` function over the pure `purchaseSuggestions`; picking a suggestion re-adds the target List's done Item with the same key (`readdPurchasedItem`, author becomes the current Member) or adds a new Item. `scripts/migrate-purchase-memory.ts` back-filled entries from done Items once.

All Members are equal — no owner/admin role, any Member can mutate any List/Item. Removing a Member is a manual Firestore console operation, not an in-app action. Lists are hard-deleted with cascade delete of their Items (ADR 0001, deliberately no soft-delete/trash).

`ShoppingItem.activeOrder` is a **fractional index** (float, not sequential integer) — reordering writes only the moved item's single document, computed as the midpoint between its new neighbors (`reorderActiveItems`/`insertActiveOrder` in `src/features/items/itemService.ts`; `planReorder` turns a same-list drop into that order and is shared by the single-list drag hook `useActiveItemsReorder` and `planDragEnd`). `sortItems` narrows active items to `ActiveItem` (`activeOrder: number`, `src/features/items/types.ts`) so the ordering math needs no null checks or casts. This is deliberate (ADR 0002): dense integer reindexing would require a batch rewrite of the whole list on every drag, which two Members dragging concurrently on different devices could race and clobber. Don't "simplify" this to integer indices.

Security is entirely rule-based (`firestore.rules`), not enforced by the client: `isMember(familyId)` checks that `families/{familyId}/members/{uid}` exists for the caller. A signed-in non-member reading their own not-yet-existing `members/{uid}` doc gets `PERMISSION_DENIED` by design — `subscribeMembership` (`src/features/auth/membershipApi.ts`, consumed by `useMembership`) treats an error on that listener as the expected "not a member yet" signal, not a fatal error.

## Architecture

- **Layering** (full rules and rationale in [`docs/conventions.md`](docs/conventions.md)): a component only renders → a `useX` hook holds state and wiring → `xService.ts` holds pure business logic (no React, no Firebase runtime imports) and `xApi.ts` holds Firestore/Firebase I/O. ESLint enforces it: components/`*.tsx` can't import `firebase/*`, `@/lib/firebase` or any `*Api`; `*Service.ts` can't import React, `firebase/*` runtime (type-only is fine), `@/lib/firebase` or `*Api`.
- **`src/features/{auth,lists,items,allLists}/`** — one directory per domain feature; dependency direction is `allLists → lists, items, auth` and `lists`/`items` never import `allLists` (ESLint-enforced). `allLists` is the All Lists screen: `useAllListsScreen` subscribes to every list's items once (`useItemsByList`) and composes single-intent hooks (`useCollapsedSections`, `useAllListsDrag`, `useAddTarget`, `useDoneItemsActions`) that close over that data directly; each `AllListsSection` receives its sorted active items as a prop and gets its per-list row wiring (actions, editing, swipe) from `useAllListsSection`, and the pure parts (done-items merge, drop resolution, `planDragEnd`) live in `allListsService.ts`. `src/screens/ListsScreen.tsx` (+ `useListsScreen.ts`) is the composition root that switches between the single-list view and All Lists, which is why it lives outside any one feature. The screen hooks (`useAllListsScreen`, `useShoppingListScreen`, `useListsScreen`) return each composed hook's own result as a group (`drag`, `addTarget`, `createForm`, `renameForm`, `actions`, ...) rather than re-listing fields; `useListsScreen` also exposes `onSignOut` (screens may call `authApi`). The combined Done section's handlers are addressed by item id alone (the origin list is looked up from the merged done items) so memoized `DoneItemRow`s get stable props.
- **`*Api.ts`** (`itemApi`, `listApi`, `inviteApi`, `membershipApi`, `authApi`) are the only modules that touch Firestore/Auth. Every Firestore-calling function takes an optional trailing `Firestore` instance (defaults to the real `db`) so tests can inject a `RulesTestEnvironment`-backed one (`authApi` talks to Firebase Auth and is the exception); Firestore collection paths live only in `src/lib/firestorePaths.ts` (constants for fixed paths, `itemsCollectionPath(listId)` as the only function; documents are addressed as collection path + id, in `*Api.ts`, `scripts/seed.ts` and `e2e/fixtures.ts` alike). `createList` takes a required `listId`: `useCreateListForm` always mints it with `generateListId()` so the online and offline create flows differ only in whether they await the write. Form failure codes are typed unions (`AddItemError`, `CreateListError`, `RenameListError`, like `RedeemError`). **`*Service.ts`** (`itemService`: sort/patch/reorder math, `listService`: name validation, `authService`, `allListsService`) are pure and unit-tested without any emulator; the `*Api.ts` modules are exercised by the `*.integration.test.ts` suites under `src/test/`.
- **Imports**: `@/` maps to `src/` (tsconfig + vite/vitest configs); same-folder imports stay `./x`. No `index.ts` barrels. Unit tests live in a `__tests__/` folder next to the code (`foo.ts` → `__tests__/foo.test.ts`); emulator suites stay in `src/test/`.
- **`App.tsx`** is a single state-machine gate, not a router: `authLoading → !user (SignInScreen) → membership loading → non-member (InviteCodeScreen) → ListsScreen` (`src/screens/`). There is no client-side router or index/landing page — list switching inside `ListsScreen` is an overlay (`ListSwitcherOverlay`), not a route, to preserve the "one screen" mobile UX. Everything past the sign-in gate reads the uid through `useSignedInUid()` (`src/features/auth/`), which returns a `string` and throws without a user, so no hook below the gate takes `uid: string | null` or re-checks it; only `useMembership` takes a nullable uid, because App calls it before sign-in.
- **Realtime data** (`subscribeItems`/`subscribeLists` in `itemApi`/`listApi`, wrapped by the `useItems`/`useItemsByList`/`useLists` hooks) subscribe via `onSnapshot` with `includeMetadataChanges: true` and stamp each doc with a client-only `pendingSync: docSnap.metadata.hasPendingWrites` flag (never persisted to Firestore) — this is how the UI shows optimistic/offline state. `src/lib/useOnlineStatus.ts` separately tracks `navigator.onLine` for the offline banner.
- **`src/lib/firebase.ts`** initializes the Firebase app under an explicit name (`'zoznam-nakupny'`, not `'[DEFAULT]'`) specifically so integration tests can `initializeApp()` a second, colliding-free instance against the emulators. Persistent offline cache (`persistentLocalCache` + multi-tab manager) is only enabled outside `MODE === 'test'` since jsdom has no IndexedDB. When `VITE_USE_FIREBASE_EMULATOR=true`, it also installs `window.__e2eSignIn`, a test-only hook Playwright uses to exchange an admin-minted custom token for a real signed-in session (there's no way to drive the real Google OAuth popup from Playwright).
- **`useSwipeActions.ts`** implements custom swipe-to-reveal-actions using Pointer Events rather than Touch Events specifically so its handlers never collide with `@dnd-kit`'s own `TouchSensor`/`MouseSensor` listeners on the same element; direction is resolved via an 8px dead zone matching dnd-kit's own touch activation tolerance. Rows are controlled: which row is open lives only in the parent list's `useSwipeRowRegistry` (`openSwipeItemId`), `useSwipeActions` tracks the in-flight drag offset, reports where a gesture ended via `onOpenChange`, runs the row tap (`onTap`: check/uncheck on a single click outside the row's own controls) and swallows the click ending a swipe or closing an open row (including another row's, flagged by the registry), and row callbacks are id-addressed (`onSwipeOpenChange(id, open)`, like `onCheck(id)`) so lists pass one stable handler to every memoized row.
- **PWA**: `VitePWA` in `vite.config.ts` (manifest + Workbox `generateSW`, production builds only; dev and e2e run without a service worker). `registerType: 'prompt'`: `useServiceWorkerUpdate` (`src/lib/`, mounted once via `ServiceWorkerUpdatePrompt` in `main.tsx`) shows a sticky "Obnoviť" toast (`notifyWithAction` in `src/lib/toaster.ts`) instead of reloading under the user, and polls for updates hourly. `navigateFallbackDenylist` keeps Firebase Hosting's reserved `/__/` URLs (the `/__/auth/handler` of the same-origin redirect sign-in) out of the cached app shell — don't drop it. The Nunito font is self-hosted (`@fontsource-variable/nunito`, imported in `main.tsx`; only its latin/latin-ext subsets are precached) so the first offline launch already has it. `firebase.json` serves `sw.js`, `workbox-*.js`, the manifest and `index.html` with `no-cache`. Icons in `public/` are generated from `public/logo.svg` by `npx pwa-assets-generator` (`pwa-assets.config.ts`) and committed.
- E2e fixtures (`e2e/fixtures.ts`) seed state directly through `firebase-admin` (bypassing security rules, mirroring the integration tests' pattern) rather than driving the UI, then hand off a custom token to `window.__e2eSignIn`.
