# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mobile-first family shopping list app. Google sign-in, join via invite code, realtime sync of shared shopping lists across family members. Vite + React 19 + TypeScript + Chakra UI, backend is Firebase (Auth, Firestore, Hosting). Domain glossary is in `CONTEXT.md`; architectural decisions with their rejected alternatives are in `docs/adr/`.

## Commands

```bash
npm run dev              # Vite dev server on :5173
npm run check            # single quality gate: lint + format:check + typecheck + unit tests + build (what CI job 1 runs)
npm run build             # tsc -b typecheck + Vite production build to dist/
npm run typecheck      # tsc -b over app, node/configs/scripts, e2e and the emulator suites (all strict)
npm run lint               # eslint . --max-warnings 0 (includes curly: all)
npm run format            # Prettier --write (format:check to verify)
npm run test               # Vitest unit tests (jsdom, no emulator needed)
npm run test:watch    # Vitest watch mode
npm run test:rules       # Firestore security rules tests — wraps itself in firebase emulators:exec, needs JDK 21+
npm run test:integration # Firestore integration tests — wraps itself in firebase emulators:exec, needs JDK 21+
npm run test:e2e        # Playwright — does NOT auto-start emulators; spawns its own dev server via webServer
npm run seed               # Generates the (one-time, static) family invite code — requires Firestore emulator already running
```

Run a single unit test file: `npx vitest run src/features/items/__tests__/itemService.test.ts`. Run a single rules/integration test file by editing the relevant config's `include` or use `npx vitest run -c vitest.integration.config.ts src/test/items.integration.test.ts` (still needs to run inside `firebase emulators:exec`, so prefer wrapping manually: `firebase emulators:exec --only firestore,auth "npx vitest run -c vitest.integration.config.ts src/test/items.integration.test.ts"`).

For e2e tests that need a signed-in member (`e2e/mobile-smoke.spec.ts`, `e2e/offline-sync.spec.ts`), the Auth + Firestore emulators must be running separately since Playwright only starts the dev server, not the emulators:

```bash
firebase emulators:exec --only firestore,auth "npm run test:e2e"
```

`e2e/smoke.spec.ts` is unauthenticated and works without emulators.

There are three separate Vitest configs (`vite.config.ts` for unit, `vitest.rules.config.ts`, `vitest.integration.config.ts`) selected by filename suffix: `**/*.rules.test.ts` and `**/*.integration.test.ts` run only under their emulator configs (the unit config excludes both globs); every other `*.test.ts(x)` is a unit test. A new suite just needs the right suffix. The emulator suites are typechecked via `tsconfig.emulator-tests.json`.

Tooling: Prettier (no semicolons, single quotes, 80 cols; markdown not formatted) and ESLint are enforced by a husky pre-commit hook (lint-staged: `eslint --fix` + `prettier --write`, no tests) and by CI (`.github/workflows/ci.yml`: `npm run check`, plus `test:rules` and `test:integration` with Java 21; e2e is not in CI). Node version is pinned in `.nvmrc` (24).

## Firestore data model

Single-tenant: one Firebase project = one Family, forever. `FAMILY_ID` (`src/constants/family.ts`) is a hardcoded constant, never looked up at runtime — there is no multi-family concept anywhere in the code.

```
families/{FAMILY_ID}                          (fixed id)
families/{FAMILY_ID}/members/{uid}            membership doc; existence = "is a member"
families/{FAMILY_ID}/lists/{listId}           name, createdAt, createdBy
families/{FAMILY_ID}/lists/{listId}/items/{itemId}
invites/{inviteCode}                          one-time, generated by scripts/seed.ts, never via UI
```

All Members are equal — no owner/admin role, any Member can mutate any List/Item. Removing a Member is a manual Firestore console operation, not an in-app action. Lists are hard-deleted with cascade delete of their Items (ADR 0001, deliberately no soft-delete/trash).

`ShoppingItem.activeOrder` is a **fractional index** (float, not sequential integer) — reordering writes only the moved item's single document, computed as the midpoint between its new neighbors (`reorderActiveItems` in `src/features/items/itemService.ts`). This is deliberate (ADR 0002): dense integer reindexing would require a batch rewrite of the whole list on every drag, which two Members dragging concurrently on different devices could race and clobber. Don't "simplify" this to integer indices.

Security is entirely rule-based (`firestore.rules`), not enforced by the client: `isMember(familyId)` checks that `families/{familyId}/members/{uid}` exists for the caller. A signed-in non-member reading their own not-yet-existing `members/{uid}` doc gets `PERMISSION_DENIED` by design — `subscribeMembership` (`src/features/auth/membershipApi.ts`, consumed by `useMembership`) treats an error on that listener as the expected "not a member yet" signal, not a fatal error.

## Architecture

- **Layering** (full rules and rationale in [`docs/conventions.md`](docs/conventions.md)): a component only renders → a `useX` hook holds state and wiring → `xService.ts` holds pure business logic (no React, no Firebase runtime imports) and `xApi.ts` holds Firestore/Firebase I/O. ESLint enforces it: components/`*.tsx` can't import `firebase/*`, `@/lib/firebase` or any `*Api`; `*Service.ts` can't import React, `firebase/*` runtime (type-only is fine), `@/lib/firebase` or `*Api`.
- **`src/features/{auth,lists,items,allLists}/`** — one directory per domain feature; dependency direction is `allLists → lists, items, auth` and `lists`/`items` never import `allLists` (ESLint-enforced). `allLists` is the All Lists screen: `useAllListsScreen` only composes single-intent hooks (`useCollapsedSections`, `useItemRegistry`, `useAllListsDrag`, `useAddTarget`, `useDoneItemsActions`), each `AllListsSection` gets its per-list wiring from `useAllListsSection`, and the pure parts (done-items merge, drop resolution, `planDragEnd`) live in `allListsService.ts`. `src/screens/ListsScreen.tsx` (+ `useListsScreen.ts`) is the composition root that switches between the single-list view and All Lists, which is why it lives outside any one feature.
- **`*Api.ts`** (`itemApi`, `listApi`, `inviteApi`, `membershipApi`, `authApi`) are the only modules that touch Firestore/Auth. Every function takes an optional `Firestore` instance (defaults to the real `db`) so tests can inject a `RulesTestEnvironment`-backed one; Firestore collection paths live only in `src/lib/firestorePaths.ts`. **`*Service.ts`** (`itemService`: sort/patch/reorder math, `listService`: name validation, `authService`, `allListsService`) are pure and unit-tested without any emulator; the `*Api.ts` modules are exercised by the `*.integration.test.ts` suites under `src/test/`.
- **Imports**: `@/` maps to `src/` (tsconfig + vite/vitest configs); same-folder imports stay `./x`. No `index.ts` barrels. Unit tests live in a `__tests__/` folder next to the code (`foo.ts` → `__tests__/foo.test.ts`); emulator suites stay in `src/test/`.
- **`App.tsx`** is a single state-machine gate, not a router: `authLoading → !user (SignInScreen) → membership loading → non-member (InviteCodeScreen) → ListsScreen` (`src/screens/`). There is no client-side router or index/landing page — list switching inside `ListsScreen` is an overlay (`ListSwitcherOverlay`), not a route, to preserve the "one screen" mobile UX.
- **Realtime data** (`subscribeItems`/`subscribeLists` in `itemApi`/`listApi`, wrapped by the `useItems`/`useLists` hooks) subscribe via `onSnapshot` with `includeMetadataChanges: true` and stamp each doc with a client-only `pendingSync: docSnap.metadata.hasPendingWrites` flag (never persisted to Firestore) — this is how the UI shows optimistic/offline state. `src/lib/useOnlineStatus.ts` separately tracks `navigator.onLine` for the offline banner.
- **`src/lib/firebase.ts`** initializes the Firebase app under an explicit name (`'zoznam-nakupny'`, not `'[DEFAULT]'`) specifically so integration tests can `initializeApp()` a second, colliding-free instance against the emulators. Persistent offline cache (`persistentLocalCache` + multi-tab manager) is only enabled outside `MODE === 'test'` since jsdom has no IndexedDB. When `VITE_USE_FIREBASE_EMULATOR=true`, it also installs `window.__e2eSignIn`, a test-only hook Playwright uses to exchange an admin-minted custom token for a real signed-in session (there's no way to drive the real Google OAuth popup from Playwright).
- **`useSwipeActions.ts`** implements custom swipe-to-reveal-actions using Pointer Events rather than Touch Events specifically so its handlers never collide with `@dnd-kit`'s own `TouchSensor`/`MouseSensor` listeners on the same element; direction is resolved via an 8px dead zone matching dnd-kit's own touch activation tolerance.
- E2e fixtures (`e2e/fixtures.ts`) seed state directly through `firebase-admin` (bypassing security rules, mirroring the integration tests' pattern) rather than driving the UI, then hand off a custom token to `window.__e2eSignIn`.
